# API Direction Brainstorm

## Goal

Define the next public APIs for this codebase without fighting the current architecture:

- Items API
- Component replication via Tether
- Hot-reload + bootstrap API
- Prebuilt Centurion commands with consumer composition

## Current Architecture Snapshot

### Matter package

- `packages/matter/src/index.ts` exports `pipeline`, `components`, `start`, `hooks`, `replication`, `network`, and `templates`.
- `packages/matter/src/network/packets.ts` is still the real network transport contract. It is ByteNet-based and hardcodes one packet per replicated component.
- `packages/matter/src/systems/server/network/replicationManager/index.ts` and `packages/matter/src/systems/client/network/replicationManager/index.ts` are the live replication path.
- `packages/matter/src/network/replication/{serverRegistry,clientRegistry}.ts` already provide a cleaner serializer/deserializer registry abstraction, but they are not wired into the live replication managers.
- `packages/matter/src/replication/{createReplicationBuilder,presets}.ts` and `packages/matter/src/templates.ts` already expose a composition layer that is much more extension-friendly than the live ByteNet replication path.
- `packages/matter/src/utils/item.ts` already contains the real item helpers, but they are internal and not exported as a stable package API.
- `packages/matter/src/items/*` already own item definitions, descriptions, serializers, and numeric ID mapping.

### Platform package

- `packages/platform/src/bootstrap/{client,server}.ts` already expose a minimal bootstrap API with a dev/prod split and hot-reload containers.
- Those bootstrap APIs only resolve boundaries and call `start(...)`; they do not provide a richer lifecycle or composition API.
- `packages/platform/src/centurion/commands/*` already contains a non-trivial built-in command set.
- `packages/platform/src/centurion/type.ts` already merges built-in Centurion user types, but only from internal modules.
- `packages/platform/src/centurion/utility.ts` already exposes reusable factories for custom Centurion types.
- There is no first-class public API for merging built-in and consumer Centurion commands/types.

## What The Existing Code Suggests

The codebase already has a strong separation between:

1. Runtime systems
2. Template/pipeline composition
3. Packet transport details

That means the cleanest direction is not to add more hardcoded managers. The cleanest direction is to finish the abstraction layers that already exist and make them public.

## Problem Decomposition

These should be treated as four related but distinct API projects:

1. Replication transport and registration
2. Public item surface
3. Bootstrap lifecycle / hot-reload surface
4. Centurion built-ins and merge API

They are related because they should feel like one package family, but they do not need to be implemented as one giant change.

## Approaches

### Approach A: Keep ByteNet, add nicer wrappers

- Expose the existing item helpers.
- Add a higher-level bootstrap wrapper around existing `bootstrapClient` / `bootstrapServer`.
- Export built-in Centurion commands and types.
- Leave replication transport mostly ByteNet-based.

Pros:

- Smallest migration.
- Lowest short-term risk.

Cons:

- Does not deliver the requested Tether replication direction.
- Leaves the core networking abstraction inconsistent.
- Risks creating a second thin API over a hardcoded transport.

### Approach B: Replace the live replication path with a package-owned Tether contract and registry

Recommended.

- Introduce a package-owned Tether replication channel.
- Move the live replication managers from barrel lookups to runtime registries/codecs.
- Keep entity lifecycle semantics (`SpawnEntity`, `DespawnEntity`, server/client entity mapping) intact.
- Promote items/bootstrap/Centurion around this composition model.

Pros:

- Matches the requested Tether direction.
- Reuses the codebase's existing composition and registry instincts.
- Creates a real consumer extension point instead of more hardcoded cases.

Cons:

- Touches the most important runtime path.
- Requires a clear decision on how custom component payloads are declared.

### Approach C: Hybrid transport layer with ByteNet compatibility and Tether opt-in

- Add a transport-agnostic replication facade.
- Keep current ByteNet replication alive while adding a second Tether-backed path.
- Migrate built-ins later.

Pros:

- Lowest migration pressure on current users.
- Easier rollout if there are existing downstream consumers.

Cons:

- Highest design complexity.
- Likely overkill for this repository state.
- Risks maintaining two replication stacks for too long.

## Recommendation

Approach B is the strongest fit.

The codebase already has unfinished abstractions for replication registries and template composition. Completing that work is cleaner than adding another wrapper layer on top of the hardcoded ByteNet managers.

The important constraint is that Tether needs statically declared message shapes. That means we should not promise arbitrary runtime-defined message contracts if the transformer cannot support them cleanly. The safest design is:

- package-owned static Tether channels
- package-owned runtime codec/handler registry
- user extension through codec registration, not module augmentation magic

## Recommended Design Direction

### 1. Replication API

Use one package-owned replication channel plus a runtime codec registry.

Recommended shape:

- one static Tether message for replication traffic
- payload includes `componentKey`, `serverEntityId`, and encoded payload data
- package-owned server/client codec registries resolve serializers and deserializers at runtime
- built-ins register through the same public API as consumers

Why this fits the codebase:

- avoids hardcoding one Tether message per component in the public API
- avoids consumer-side edits to package source
- aligns with the existing `network/replication/*Registry.ts` direction
- keeps entity spawn/despawn rules separate and explicit

Non-goal:

- do not try to let consumers invent compile-time Tether message ids from outside the package

### 2. Items API

Promote a stable public items module rather than asking consumers to deep-import `utils/item.ts`.

Recommended shape:

- export `items/*` from the root package
- add a focused public `items/api.ts` or similar facade that exposes the stable helpers only
- include item creation, ID conversion, item config/model/tool lookup, and safe container mutation helpers
- keep low-level replication serializers as internal unless there is a clear external use case

Why this fits the codebase:

- the functionality already exists
- the missing piece is API shaping and export policy, not greenfield logic

### 3. Bootstrap + hot-reload API

Keep the existing `bootstrapClient` / `bootstrapServer` core, but add a higher-level composition API instead of replacing them.

Recommended shape:

- preserve current low-level bootstrap functions
- add a builder/factory around them for:
    - production module discovery
    - dev hot-reload containers
    - optional system/template extensions
    - explicit bootstrap boundary inspection when needed
- expose a small API that returns the started world/crate and the resolved boundary metadata

Why this fits the codebase:

- current code already separates boundary resolution from startup
- this is an additive API, not a risky rewrite

### 4. Centurion API

Treat built-ins as a package-owned preset that consumers can merge with their own modules.

Recommended shape:

- export built-in command modules explicitly
- export built-in type modules explicitly
- add a helper like `createCenturionUserTypes(...)` or `mergeCenturionTypes(...)`
- add a helper that returns the built-in command modules as a list/object for consumers to combine with their own registration modules

Important limitation:

- decorator-registered Centurion commands are side-effect based, so the merge API likely needs to be about module sets / import surfaces rather than runtime command objects

Why this fits the codebase:

- built-ins already exist
- `centurion/type.ts` already demonstrates the merge pattern for types
- consumers mostly need a supported way to compose, not a new command system

## Proposed Delivery Order

### Phase 1: Replication foundation

- Decide the Tether contract shape.
- Replace barrel-based replication lookup with public runtime registries/codecs.
- Migrate built-in replicated components to register through that API.
- Preserve existing spawn/despawn and entity map semantics.

### Phase 2: Public Items API

- Export a stable items surface from `@lisachandra/matter`.
- Separate stable consumer helpers from internal replication plumbing.
- Ensure item replication code uses the same public item metadata sources.

### Phase 3: Bootstrap API

- Add an additive bootstrap composition layer over current client/server bootstrap functions.
- Make dev hot-reload and production discovery use the same option shape.

### Phase 4: Centurion built-ins

- Expose built-in commands/types as first-class exports.
- Add helpers for merging user-defined types with built-ins.
- Document the supported composition pattern for user commands.

## Key Risks

- Tether compile-time constraints may force a narrower custom-component story than the leftover plan assumes.
- Replacing the live replication path is riskier than the other three API additions.
- Centurion command composition may be more about package structure and exports than runtime merging, because decorators register by import side effect.

## Design Rules To Follow

- Prefer additive APIs over rewrites where possible.
- Use one extension story per subsystem, not multiple overlapping stories.
- Keep built-ins and user extensions on the same code path.
- Do not require consumer-side module augmentation for runtime behavior.
- Keep entity lifecycle replication separate from component payload codec logic.

## First Implementation Slice

If we want the best leverage, the first slice should be:

1. finalize the replication contract
2. wire registries into the live replication managers
3. migrate one built-in replicated component end-to-end as the reference path
4. then shape the public API around that pattern

## Decisions Made

1. Replication should use a single generic package-owned Tether channel keyed by `componentKey`.
2. Built-ins and user extensions should register through the same runtime codec path.
3. Centurion should expose explicit preset APIs for built-in commands/types instead of relying on side-effect imports as the primary composition story.
4. The Items API should be available from both the root `@lisachandra/matter` export and a dedicated `@lisachandra/matter/items` subpath.

## Resulting Implementation Outline

### 1. Matter replication foundation

- Add a package-owned Tether replication contract centered on one generic component replication channel.
- Encode payloads as `{ componentKey, serverEntityId, blobs?, buf? }` or the equivalent final transport shape.
- Preserve explicit entity lifecycle messages/behavior for spawn and despawn.
- Replace barrel-based serializer/deserializer lookup in the live replication managers with public runtime codec registries.
- Register built-in codecs through the same API that user code will call.

### 2. Public Items API

- Promote stable item helpers into a supported public surface instead of relying on `utils/item.ts` deep imports.
- Export item definitions/descriptions/serdes/types from both the root package and `@lisachandra/matter/items`.
- Add a focused public facade for safe helpers such as item creation, ID conversion, config lookup, and container mutation.
- Keep low-level replication internals internal unless a concrete consumer need appears.

### 3. Bootstrap and hot-reload API

- Keep `bootstrapClient` and `bootstrapServer` as the low-level primitives.
- Add a higher-level composition API that standardizes:
    - production module discovery
    - development hot-reload containers
    - optional system/template extensions
    - inspection of the resolved bootstrap boundary
- Make this additive so current consumers can migrate gradually.

### 4. Centurion preset API

- Export built-in command modules and type modules as first-class public modules.
- Add preset helpers that let consumers opt into built-ins explicitly during bootstrap.
- Add a typed helper for merging built-in and consumer Centurion user types.
- Document command composition around preset/module inclusion, not runtime mutation of decorator state.

## Recommended Execution Order

1. Implement the replication foundation first, because it is the most architectural and the other APIs should align with its extension story.
2. Expose the public Items API next, because most of the logic already exists and only needs surfacing/cleanup.
3. Add the bootstrap composition layer third, because it is mostly additive over the current low-level API.
4. Finish with the Centurion preset API, which is primarily export/composition work after the bootstrap story is settled.

## Success Criteria

- Consumers can register a custom replicated component without editing package source.
- Built-in replicated components and custom ones use the same codec registration flow.
- Consumers can use items through supported exports without deep-importing internal files.
- Consumers can bootstrap client/server runtime with one explicit API for dev and production concerns.
- Consumers can opt into built-in Centurion commands/types through explicit preset APIs and merge their own cleanly.
