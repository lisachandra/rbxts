# Matter Public Items API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Design and implement a consumer-facing `@lisachandra/matter/items` API that is stable for downstream callers, exposes the expected item helpers and aliases, and keeps internal world/store behavior separate from the public package surface.

**Architecture:** Make `packages/matter/src/items/*` the canonical public API layer. Keep pure item data, numeric id mapping, and consumer-safe item list helpers in `src/items/api.ts`, and move package-runtime Roblox instance lookup helpers into that same public layer so consumers no longer hit stubbed `undefined` exports. Keep `packages/matter/src/utils/item.ts` as the internal world/store API for ECS entity operations, with shared low-level lookup logic either duplicated minimally or extracted later only if needed.

**Tech Stack:** roblox-ts, Matter ECS, Roblox `ReplicatedStorage`, package subpath exports in `packages/matter/package.json`

---

## Current State

**Observed public API gaps:**
- `packages/matter/src/items/api.ts` implements pure data helpers like `getCompleteItem`, `getItemConfig`, `createItem`, `addItem`, `removeItem`, and `moveItem`.
- The same file exports `getItemModelContainer`, `getItemToolContainer`, `getItemToolAnimationContainer`, `getItemModel`, `getItemTool`, and `getItemToolAnimation`, but all currently return `undefined`.
- `packages/matter/src/items/index.ts` exports lowercase `serdes` and `unreplicatedItems`, but downstream callers already expect capitalized public aliases `Serdes` and `UnreplicatedItems`.
- `packages/matter/src/items/definitions.ts`, `descriptions.ts`, and `serdes.ts` are currently placeholder-level, so a good public API design must account for the item data layer and not only the helper exports.

**Observed downstream expectations:**
- `packages/matter/src/systems/server/network/itemsSerializer.ts` imports `getNumericItemIdFromId`, `Serdes`, and `UnreplicatedItems` from `shared/items`.
- `packages/matter/src/systems/client/network/itemsDeserializer.ts` imports `getItemIdFromNumericId` and `Serdes` from `shared/items`.
- Internal runtime item systems already rely on `getItemTool` from `shared/utils/item` for real Roblox `Tool` lookup behavior.

**Implication:**
A good public API should not invent a new shape. It should provide the helpers and aliases that downstream code is already written against, while separating those from entity/world mutation helpers that belong in `utils/item.ts`.

---

## Approaches

### Option 1: Thin Compatibility Layer In `src/items` (Recommended)

Expose the existing consumer-safe helper set from `src/items/api.ts`, add real Roblox instance lookup implementations there, and export capitalized compatibility aliases from `src/items/index.ts`.

**Pros:**
- Preserves the intended package boundary: `src/items/*` is public, `src/utils/item.ts` stays internal.
- Smallest behavior change for consumers already importing from `@lisachandra/matter/items` or `shared/items`.
- Avoids coupling the public API to `store.world` and entity mutation logic.

**Cons:**
- Duplicates a little runtime lookup logic currently present in `utils/item.ts`.
- Requires carefully choosing which helpers are public and which remain internal.

### Option 2: Re-export `utils/item.ts` Through The Public API

Make `src/items/index.ts` or `src/items/api.ts` delegate broadly to `src/utils/item.ts`, exposing nearly all current runtime helper behavior to consumers.

**Pros:**
- Fastest path to make the public exports “work”.
- Reduces duplicated code immediately.

**Cons:**
- Leaks internal ECS/store-oriented behavior into the public package surface.
- Makes future cleanup harder because public imports start depending on internal implementation details.
- Risks exposing helpers whose signatures are not consumer-friendly, such as entity-based mutation functions.

### Option 3: Breaking Pure-Data Public API

Keep `src/items/api.ts` pure-data only, remove runtime lookup helpers from the public surface, and require consumers to use a different runtime module.

**Pros:**
- Cleanest separation long-term.
- Simplifies the public API contract.

**Cons:**
- Breaking for any existing callers expecting runtime item lookup helpers.
- Conflicts with the current package export shape and downstream usage patterns.

**Recommendation:** Option 1. It preserves the public `items` entrypoint as the user-facing API without leaking internal store/world behavior.

## Recommended Design

### Public API Boundary

`packages/matter/src/items/*` should own the public item contract. After implementation, consumers of `@lisachandra/matter/items` and root `@lisachandra/matter` should be able to rely on:
- item definitions and path types
- descriptions and images
- numeric id mapping helpers
- serializer tree aliases
- unreplicated-key registry alias
- item creation and list mutation helpers
- runtime Roblox instance lookups for models, tools, and tool animations

The public API should not expose ECS entity-based inventory operations such as:
- `addItem(entityId, location, item)` from `utils/item.ts`
- `moveItem(entityId, guid, destination)` from `utils/item.ts`
- `spawnItem(item, cf)` from `utils/item.ts`

Those remain internal because they depend on `store.world`, Matter components, and workspace/entity semantics.

### File Responsibilities

- `packages/matter/src/items/definitions.ts`
  - owns the canonical item definition tree and `ValidItemPath`
  - exports both lowercase runtime values and optional compatibility aliases if needed
- `packages/matter/src/items/descriptions.ts`
  - owns the public description/image tree matching the item hierarchy
- `packages/matter/src/items/serdes.ts`
  - owns the serializer tree and should export a capitalized alias `Serdes`
- `packages/matter/src/items/api.ts`
  - owns all public helper functions
  - should implement Roblox instance lookup helpers instead of returning `undefined`
- `packages/matter/src/items/index.ts`
  - aggregates the public surface
  - should export compatibility aliases like `Serdes` and `UnreplicatedItems`
- `packages/matter/src/utils/item.ts`
  - remains internal for world/store/entity operations
  - may keep its own runtime helpers unless later extraction becomes worthwhile

### Runtime Lookup Design

The public API should implement the runtime lookup helpers directly in `src/items/api.ts` using `ReplicatedStorage`, matching current internal behavior from `utils/item.ts`:
- `ReplicatedStorage.Models.Items`
- `ReplicatedStorage.Tools`
- `ReplicatedStorage.Animations.Tools`

Recommended design:
- keep the generic path walker local to `src/items/api.ts`
- return `N<Model>`, `N<Tool>`, and `N<Animation>` rather than broad `Instance`
- make the container helpers return the path-resolved folder/container, and the non-container helpers return the named child (`"Model"`, `"Tool"`, `"Animation"`) exactly like the internal runtime API does today

This gives consumers the same practical runtime behavior without depending on internal ECS utilities.

### Compatibility Aliases

Downstream code already expects capitalized names. The public API should provide them explicitly rather than forcing consumers to use internal lowercase names:
- `Items` for the definition tree value if that name is desired publicly
- `Serdes` for the serializer tree value
- `UnreplicatedItems` for the unreplicated-key map
- optionally `Descriptions` only if a value alias is actually useful; otherwise keep only `descriptions`

The public API should not rely on consumers knowing lowercase internal names.

### Data Model Expectations

The item definition tree must be non-empty enough for the public API to be meaningful. At minimum, restore the paths already referenced elsewhere in the package so public `ValidItemPath`, `getItemConfig`, `getCompleteItem`, `getNumericItemIdFromId`, and `getItemIdFromNumericId` have a concrete backing tree.

Because the old generated Roblox configuration objects are gone, the new public contract should be explicit:
- config values are plain roblox-ts tables and primitives
- path segments remain PascalCase
- merged item data remains lowercase-keyed and excludes child PascalCase branches
- serializer traversal continues to walk the same PascalCase path hierarchy

- [ ] **Step 1: Add a local instance path walker to `src/items/api.ts`**

Implement a helper equivalent to the internal `getInstanceFromPaths` logic so the public API can resolve path-based Roblox instances without importing `utils/item.ts`:

```ts
function getInstanceFromPaths<T extends Instance>(root: T, strict = false) {
	return (paths: ValidItemPath): N<T> => {
		let current: N<Instance> = root;
		for (const segment of paths) {
			current = current?.FindFirstChild(segment) ?? (strict ? undefined : current);
		}
		return current as N<T>;
	};
}
```

Expected result: `api.ts` can implement the container helpers directly.

- [ ] **Step 2: Wire `ReplicatedStorage` containers in `src/items/api.ts`**

## Notes

- This plan intentionally does not expose `utils/item.ts` entity/world mutation helpers through the public package surface.
- If future consumers need a runtime-only subpath such as `@lisachandra/matter/items/runtime`, that should be a separate design pass rather than mixed into this compatibility fix.
- The current package build has unrelated replication and module-resolution issues in other files. Verification for this work should focus on whether the public item API compiles and matches current consumer expectations.
- If the user wants stricter backwards compatibility with the old generated Roblox configuration instances, that is a different scope from this plan. This plan preserves helper names and practical behavior, not the old `Folder`/`ValueBase` instance shapes.
